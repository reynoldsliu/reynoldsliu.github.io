LLM 應用工程的演化規律：從 prompt 到 loop，以及下一步

2026-07 · Reynolds Liu

每個新概念都在解決上一層規模化後的瓶頸

概念解決的瓶頸抽象層級
Prompt engineering單次指令怎麼寫token
Context engineering視窗裡放什麼、怎麼取捨視窗
Harness engineering模型能碰到什麼（工具／環境／權限）環境
Loop engineering時間軸上怎麼迭代、自我修正、何時停時間

新概念誕生的通則：當某個子步驟的失敗模式、技能組合、工具鏈都與母學問不同時，它就會被獨立命名 —— 如同 context engineering 曾經只是 prompt engineering 裡的一個步驟。

順推：下一個被命名的學問

  • Verification engineering（驗證工程）—— 最可能先浮現。觸發訊號：驗證難度超過生產難度（agent 產能遠大於人類審核能力）。 核心問題：如何設計「驗證成本遠低於生產成本」的任務結構、防 reward hacking 的 rubric、裁判模型、抽樣審計的統計學。
  • Orchestration / Fleet engineering（編隊工程）。multi-agent 是技術架構，fleet 是工程學問 —— 類比「多執行緒」與「並行程式設計」的關係。 任務切分、agent 間 context 傳遞協定、衝突仲裁、失敗偵測與替換、成本分配 —— 底層全是分散式系統的老問題。

斷推：打斷階梯的劇本

  • Economy engineering：中央指揮改為市場機制（競標、賞金、賠償），管理問題變成 mechanism design。
  • Ecology engineering：不設計行為、設計淘汰規則 —— 工程師從設計者變成育種者。
  • De-engineering：押注所有 engineering 都是模型不夠強時期的鷹架（如 feature engineering 被 deep learning 蒸發）， 最終只剩 intent specification：把「你要什麼」講清楚。規格書與需求分析這些最古老的技能，繞一圈變成最後的護城河。

管理工作正在變成工程物件

  • 派工判斷 → orchestrator routing 邏輯（可 code、可 A/B test）
  • Code review 品味 → rubric 檔案（可版控、可迭代）
  • Onboarding 文件 → 可載入的 agent skills（可 diff、可 rollback、可複製一萬份）
  • 換人決策 → eval 分數觸發的 agent 替換策略

差異在於：人類管理靠經驗傳承；工程物件可以 diff、rollback、測試、無限複製。

工程師的站位：押注不變量，不押工具

不變量（隨時間增值）工具（半衰期以月計）
分散式系統、OS/DB 內部原理特定 agent 框架的操作技巧
讀懂並判斷 code 好壞的能力框架細節
模糊需求 → 精確規格的表達力
統計直覺（eval/verification 的地基）

站位選擇：站在 agent 的上游（造 orchestration、sandbox、記憶系統等基礎設施）或側面（驗證 agent 產出的 eval 與可靠性工程），不站下游（明確規格的 ticket、CRUD、改 bug —— 那是 agent 最先吃掉的層）。 跳出方式：從「完成任務」改成「擁有問題」—— 一個系統從需求到上線到出事，整段能扛。

一句話總結

不需要預測哪個概念會贏，只需要站在所有劇本的交集： 深的系統底子 × 快的判斷力 × 把「要什麼」講清楚的表達力。
