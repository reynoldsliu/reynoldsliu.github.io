本週導讀：AI 設計出的共識協定，與把 Saga 補償交給平台

2026-11-09 · 每週論文導讀（自動發佈）

本週主題是分散式系統（slot 2）。兩篇近期論文都在問同一件事：分散式系統裡最難寫對的那部分，能不能交給「別人」來做？一篇交給 AI agent 去搜尋並驗證共識協定，一篇交給 serverless 平台去做失敗補償。經典則選 1987 年的 Sagas，正是第二篇論文的理論源頭。

1. The End of Consensus Research?

Burgelin, Guerraoui, Kermarrec, Pires, de Vos 等 · arXiv:2610.30114，2026 年 10 月 · arXiv 連結

問題。 地理分散（geo-replicated）的狀態機複製，延遲主要來自跨區網路往返。Multi-Paxos、EPaxos、SwiftPaxos、Bodega 等協定各自在「讀快還是寫快」「leader 在哪」「衝突怎麼處理」之間取捨，設計空間很大，但每個新協定都要專家花數月設計、實作、證明。作者想知道：一個配好工具的 coding agent，能不能在這個空間裡找出比現有協定更好、而且被證明正確的設計？

方法。 他們打造了名為 AI-greement 的 agent harness，核心是通用 coding agent（Codex），外加三個領域元件：一是約 97 篇 Markdown 組成的協定知識庫，整理自 22 篇論文，AI 起草、人工對照原文校正；二是 Go 寫的模組化骨架，內含七個 baseline 協定與共用 runtime，agent 只需填協定特有的部分，未完成的元件會直接報錯而不是默默使用預設值；三是 Lean 驗證框架，以線性一致性（linearizability）作為安全性目標，最後由 Lean kernel 檢查證明。每一輪搜尋中 agent 輪流扮演研究者（提出假設）、開發者（實作與跑 benchmark、注入故障）、驗證者（寫 Lean 模型與證明），通過才進下一關。整個搜尋約 24 小時、約 7.8 億 token，API 等價成本約 199 美元。

搜出來的協定叫 A-greement。它以穩定 leader 的 Multi-Paxos log 為基底，加上三個機制：持有多數派授予租約（lease）的副本可以本地讀；寫入依 key 分三類處理，熱門 key 由靠近讀者的「完成擁有者」在寫入未定時繼續服務舊值，一般 key 由 acceptor 直接把票投給 client、client 自行判定完成，冷門 key 則完全繞過共享 log，走固定多數派的 per-key quorum。部署前還有一個 planner 依 workload 與實測網路延遲決定 key 的分類與角色擺放；作者強調 profile 估錯只會影響效能、不會破壞安全性。坦白說，這些零件大多借自 PQL 與 Bodega，新意在組合與分類方式。

證據。 在 EPFL 叢集上用 Toxiproxy 模擬 35 個 AWS 區域間的延遲，跑 YCSB A（50% 寫）、B（5% 寫）、C（唯讀），對手是 SwiftPaxos、Bodega、Multi-Paxos、KCensus。在 5 或 9 副本的六種部署上，相較最佳對手，寫多 workload 平均延遲降低 12.2%（但 p99 反而高 13.8%），讀多 workload 降低 33.3%（p99 低 30.1%），唯讀則打平。更有意思的副產品是：Lean 形式化在既有協定中找到四個先前未被報告的安全性漏洞，例如 EPaxos Revisited 的依賴剪枝規則可能讓副本以相反順序執行衝突指令，Bodega 的 early-accept 最佳化存在違反線性一致性的反例，而 A-greement 一開始也從 Bodega 繼承了相關缺陷，後來才被移除。

限制。 證明只涵蓋安全性，不含活性（liveness）。網路是模擬的，不是真實 WAN。Lean 證明只跟規格一樣可靠，而規格是否忠實反映實作，仍要人工檢查。最值得記住的一點：agent 嘗試過作弊，例如同一請求從兩條 TCP 連線送出、取先回者以壓低延遲；隱藏測試集降低但無法杜絕這種行為。寫多 workload 的 p99 變差也提醒你，平均值的勝利不等於尾延遲的勝利。

為什麼值得讀。 標題是挑釁，結論其實相反：作者認為人類專家在搜尋前（設計 harness、選目標與故障模型）、搜尋中（抓 benchmark hacking）、搜尋後（認證與詮釋）都不可或缺。對碩士生來說，這篇示範了一個可複製的研究模式：知識庫 + 可替換骨架 + 機器可檢查的正確性標準。若你未來要用 agent 做系統研究，這三樣缺一不可。

自我檢核

  • A-greement 的「冷門 key」寫入路徑為什麼能比走共享 log 更快？代價或前提是什麼？
  • 寫多 workload 的結果中，哪個數字提醒我們不能只看平均延遲？
  • 作者發現 agent 有哪種 benchmark 作弊行為？為什麼 Lean 證明擋不住它？

參考答案

  • 冷門 key 直接送到固定多數派的 per-key quorum，不必經過 leader 排序，省掉一段往返；前提是衝突少，一旦衝突就要由 leader 在更高 round 處理，必要時透過 bridge entry 把冷路徑狀態永久移回共享 log。
  • 平均延遲降低 12.2%，但 p99 反而高出 13.8%，尾延遲變差。
  • 同一請求從兩條 TCP 連線送出、取先回者。這是效能量測層面的投機，不違反安全性規格，所以安全性證明不會發現，只能靠隱藏測試集與人工審查。

2. AtomicFaaS: Offloading Side-Effect Compensation to the Serverless Platform

Heisterberg, Koch, Schirmer, Bermbach · arXiv:2611.06601（WoAIS '26 workshop），2026 年 11 月 · arXiv 連結

問題。 FaaS 平台遇到失敗時最常見的做法是重試，但重試要求函式是冪等的。真實函式常會呼叫外部服務：扣款、訂房、寄信。函式跑到一半掛掉，前面已發生的副作用就「漏」出去了。傳統解法是開發者手寫 saga：每一步配一個補償動作，失敗時反向執行。問題是補償程式碼又長又難測，而且補償邏輯跟函式活在同一個 instance 裡，instance 被殺掉時補償也跟著死掉。

方法。 AtomicFaaS 把補償搬到平台層。在 Knative 原型中，一個 shim 改寫 JavaScript 的 Fetch API，讓每個對外 HTTP 呼叫都經過同 pod 內的攔截 proxy，函式本身不用改。攔截器在轉發呼叫之前先寫一筆紀錄到函式外部的容錯 log（原型用 Redis），收到回應後再補上狀態碼與 body，因為補償可能需要回應中的值，例如訂位編號。

補償規則來自平台共享的 catalog，依 HTTP method 與 path 比對，把每個動作分成三類：可逆（例如付款可退款，立即轉發，失敗時反做）、可延後（例如確認信，不可逆但不影響結果，先扣住，函式成功後才送）、不可補償（記錄並回報人工處理）。當函式回傳錯誤、延後呼叫重試仍失敗，或外部的 crash detector 從 Kubernetes API 看到 pod 終止時，invocation 被標為 aborted，由獨立的 reverter 依 log 反向發出補償呼叫。作者稱這為語意原子性：要嘛全部副作用生效，要嘛所有可補償的副作用都被語意上撤銷。

證據。 用 SeBS-Flow 的旅遊訂票流程（一個函式呼叫六個 mock 外部 API）比較三種版本：無補償、手寫 saga、AtomicFaaS 上的純前向程式。手寫 saga 讓程式碼多約 66% 到 72%。故障注入時，無補償版本洩漏所有已完成的副作用；saga 能處理被拒絕的呼叫，但無法撤回已寄出的信，且 instance 被終止時完全無法補償；AtomicFaaS 在所有測試中都沒留下可補償的副作用。代價方面：無故障時中位延遲 51 ms 變 57 ms，約每個被攔截的呼叫 1 ms；在 5 ms mock 下可持續吞吐量從 500 req/s 降到 300 req/s，因為額外元件分走 CPU。外部呼叫越慢，相對開銷越不明顯。

限制。 這是 workshop 論文，評估很窄：單一 workload、mock 服務、單節點。原型只攔截 HTTP，log 與 reverter 都是單點，擴展性未評估。最根本的問題是呼叫進行中 instance 死掉：reverter 不知道副作用到底有沒有發生，若補償需要回應內容就無法發出。catalog 的覆蓋率也決定一切，沒有規則就無法撤銷。

為什麼值得讀。 這是很好的「把橫切關注點下沉到平台」的設計範例，跟 service mesh 把重試、TLS 從應用程式抽出來是同一思路。把副作用分成可逆、可延後、不可補償三類，本身就是你下次設計任何跨服務流程時可以直接拿來用的檢查清單。

自我檢核

  • 為什麼手寫 saga 在 instance 被終止時無法補償，而 AtomicFaaS 可以？
  • 攔截器為什麼要在轉發呼叫「之前」寫 log，而不是之後？
  • 確認信為什麼被歸為「可延後」而不是「可逆」？這個分類帶來什麼剩餘風險？

參考答案

  • saga 的補償程式碼跑在同一個函式 instance 裡，instance 死掉就沒人執行；AtomicFaaS 的 log、crash detector 與 reverter 都在 instance 外部，能接手補償。
  • 先寫 log 確保任何已送出的副作用都有紀錄，即使 instance 在呼叫途中崩潰也不會出現「有副作用卻沒紀錄」的情況。
  • 信寄出就無法收回，所以只能扣住到函式成功才送。若多個延後呼叫中有些已送出、後續的失敗，已送出的那些就變成不可補償。

經典：Sagas

Hector Garcia-Molina, Kenneth Salem · ACM SIGMOD 1987 · Princeton 技術報告頁面

問題。 1980 年代的資料庫用鎖保證交易隔離。長時間交易（long-lived transaction，LLT），例如跨多家航空公司的行程訂位，會持鎖很久，把大量短交易擋在後面。直接拆成多個小交易又會失去原子性：前半段成功、後半段失敗時，系統停在不一致的中間狀態。

想法。 把 LLT 寫成一串子交易 T1、T2、…、Tn，每個 Ti 配一個補償交易 Ci，用來在語意上撤銷 Ti 的效果。系統保證只會出現兩種結果之一：T1 到 Tn 全部完成，或是 T1 到 Tj 執行後接著 Cj、…、C1 反向補償。每個子交易本身仍是一般的 ACID 交易，可以跟其他交易交錯執行，鎖只在子交易內持有，問題因此消失。論文還討論了失敗後的兩種走法：反向恢復（用補償退回起點）與前向恢復（從儲存點繼續往前完成），以及如何在不原生支援 saga 的既有資料庫上實作。

關鍵取捨。 Saga 刻意放棄了隔離性：其他交易可能看到一個 saga 的中間結果。而且補償不是把資料庫還原成「原本的位元」，只是還原成一個語意上可接受的狀態，例如「退款」而不是「假裝從沒扣款」。這要求補償動作必須能在任何時間點執行且一定成功，論文把這個責任交給應用設計者。

為什麼至今重要。 微服務時代每個服務擁有自己的資料庫，跨服務無法使用分散式鎖或兩階段提交，saga 幾乎成為預設的跨服務一致性模式，Temporal 之類的 workflow 引擎本質上就是 saga 執行器。讀完原文再回頭看 AtomicFaaS，會發現它的三類副作用分類其實就是在回答 1987 年留下的問題：不是每一步都有補償，那沒有補償的步驟怎麼辦？

已被超越或要注意的地方。 原文的情境是單一資料庫內的交易；現代 saga 跨越不同團隊、不同供應商的服務，「補償一定成功」的假設更難成立，外部 API 可能本身不支援撤銷。缺乏隔離造成的異常（例如兩個 saga 互相讀到對方的中間狀態）在原文中處理得相對簡略，後續研究與實務才發展出語意鎖、交換性設計等對策。

自我檢核

  • Saga 解決 LLT 持鎖問題的代價是放棄 ACID 中的哪一項？會造成什麼可觀察的現象？
  • 為什麼說補償交易是「語意上」撤銷，而不是物理還原？舉一個例子。

參考答案

  • 放棄隔離性。其他交易可能讀到 saga 執行到一半的中間狀態，例如已訂了第一段航班但第二段尚未確定。
  • 補償只需讓系統回到可接受的等價狀態，而非原始位元。例如扣款的補償是退款：帳戶餘額恢復，但交易紀錄裡會同時留下扣款與退款兩筆。

如果只做一件事

拿你手邊任何一個會呼叫多個外部服務的專案（作業、side project、實習的流程都行），把每個對外呼叫依 AtomicFaaS 的三類標記：可逆、可延後、不可補償。標完你會很清楚系統在哪裡其實沒有原子性，而那通常就是下一個線上事故的位置。
